## 1. Approval rules per org (user: "define approval at org level and on selecting types")
RLY_Org__c:
  Approval_Rule__c   Picklist restricted: Always (default) | Selected_Types | Never   (labels: Always, Only when the release contains…, Never: deploy when the checks pass)
  Approval_Types__c  MultiselectPicklist (visibleLines 6): Apex | Flows | Profiles_Permissions | Objects_Fields | Deletions | Manual_Steps | Hotfix | Other  (labels: Apex classes and triggers, Flows, Profiles and permission sets, Objects and fields, Deletions, Manual steps, Hotfixes, Anything else)

(no: Layout → Other), Deletions = release has deletions; Manual_Steps = release has manual steps; Hotfix = Is_Hotfix__c; Other = anything not in another bucket.
When the checks pass (the point today where the release becomes 'Ready for approval'): if the target org's rule says no approval is needed → record Approved_Via__c 'Rule', Approved_By__c null, Approval_Comment__c "Approved automatically: <reason>", and start the deploy exactly as an approval does (this happens in the status reader on a page read / Releases list refresh: callouts before DML; if ordering doesn't allow it, set a pending flag and dispatch on the next read — no async). ## 2. Flows: versions and activation
Select/Review: for selected Flow components, the hub reads the dev org's FlowDefinition via Tooling API (SELECT DeveloperName, ActiveVersion.VersionNumber, LatestVersion.VersionNumber, LatestVersion.Status FROM FlowDefinition WHERE DeveloperName IN :names) → new @AuraEnabled RlyChangesController.flowVersions(Id orgId, List<String> names) → List<FlowInfo{ String name; Integer latest; Integer active; String latestStatus /*Active|Draft|Obsolete|InvalidDraft*/; }>. UI shows "Version 8 · Draft" / "Version 7 · Active"; picking a Draft warns "Deploys inactive".
Per flow on Review: "After deploy" choice: Keep (default, label "Keep as in <dev org>") | Activate (label "Activate in each org") | Inactive (label "Leave inactive: add a manual step to activate"). RaiseRequest gets List<FlowChoice{ String name; String choice; }> flowChoices. Stored on the release: Flow_Actions__c LongTextArea (JSON list {name, choice}). Inactive → creates a manual step (build 14 RlyManualSteps) "Activate flow <name>", Category Setup, Timing After_Deploy, on every org.
After a successful deploy into an org (RlyDeployReader success path, and for Back_Promote syncs): for each flow with choice Activate, the hub signs in to that org (RlyOrgSession, the org's RLY_Org__c record — the hub org is registered too) and: Tooling query FlowDefinition by DeveloperName → if LatestVersion != ActiveVersion: PATCH /services/data/vXX/tooling/sobjects/FlowDefinition/<Id> body {"Metadata":{"activeVersionNumber":<latest>}}. Result per org/flow stored in Flow_Results__c LongTextArea JSON [{org, flow, version, status:'Activated'|'Already active'|'Failed', message}]. Callouts before DML. Verify with Salesforce docs (WebSearch/WebFetch allowed) whether activating via Tooling API FlowDefinition update works in production and what it needs (Manage Flow permission; flow test coverage rules apply to deploy-as-active, not to activation? confirm) and put what you found in the report and in a code comment.
Detail: List<FlowResult> flows → release page "Flows" section: "Case_Escalation · SIT v4 active · PROD v9 active" / failure reason. Promotion carries Flow_Actions__c of carried releases (union; Activate wins over Keep, Inactive manual steps already carried by build 14).
