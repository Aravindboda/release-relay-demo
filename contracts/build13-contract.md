## User story
A developer deleted components in their developer org (or wants to remove components). On New Release they can pick deletions next to changes; the release removes those components from the target branch and, on deploy, from the target org (destructiveChangesPost). Deletions travel through Promote to PROD and merge back down like any change.

## Finding deletions (Select step)
1. Orgs with source tracking (RlyChangeFinder 'tracked' mode): SourceMember rows with IsNameObsolete = true → deletion candidates (already partly read; surface them).
2. Orgs without source tracking (Metadata API): new action "Find deleted components" on the Select step. The hub lists the files under the source path on the developer org's OWN branch (RLY_Org__c.Branch__c, e.g. dev1; fall back to the first stage's branch if blank) through the Git provider (new RlyGit method listFiles(String branch, String path) → List<String> paths; GitHub: GET /repos/{repo}/git/trees/{branch}?recursive=1, filter by source path; other providers: throw the existing "isn't available for X" error), maps paths → Type:Name (classes/X.cls → ApexClass:X, triggers/X.trigger → ApexTrigger:X, lwc/x/ → LightningComponentBundle:x, aura/x/ → AuraDefinitionBundle:x, objects/O/fields/F.field-meta.xml → CustomField:O.F, objects/O/O.object-meta.xml → CustomObject:O, flows/X.flow-meta.xml → Flow:X, layouts/X.layout-meta.xml → Layout:X, permissionsets/X.permissionset-meta.xml → PermissionSet:X, labels: skip, pages/X.page → ApexPage:X, components/X.component → ApexComponent:X, staticresources/X.resource-meta.xml → StaticResource:X, tabs/X.tab-meta.xml → CustomTab:X, objects/O/validationRules/V... → ValidationRule:O.V, objects/O/recordTypes/R... → RecordType:O.R, objects/O/listViews/L... → ListView:O.L; anything else is ignored), then checks which of those still exist in the developer org with the Metadata API listMetadata the hub already uses (RlyMetadata), and returns those missing in the org.
   Honest wording in the UI: "In dev1's branch but not in DEV1. They may have been deleted in DEV1, or came from another org through the branch and were never deployed to DEV1. Tick only what you deleted." Candidates are NEVER pre-selected.
3. Manual: on Review, the existing "add a component by hand" drawer gets a choice "Add" / "Delete" (Delete = type + name, e.g. ApexClass + OldHelper).

Apex API (backend):
  RlyChangesController.findDeletions(Id orgId) → List<RlyChangeFinder.Change> with a new Boolean `deleted = true` on Change (add the field to Change; tracked-mode deletions set it too). Change keeps its existing fields (type, name, key, …).
  RlyRaiseService.RaiseRequest: ADD `List<Item> deletions` (same Item shape as items: type + name). Rules: a deletion can't also be in items ("<Type> <Name> is both added and deleted."); deleting an Apex class or trigger doesn't need a test class unless Apex is also added; test level: if only deletions of Apex → RunSpecifiedTests with any tests the user listed, else the pipeline default (RunLocalTests for PROD, NoTestRun for sandboxes) — keep simple: send tests as today; deletions alone with no Apex added → NoTestRun except the hub/production target → RunLocalTests (Salesforce requires tests when deleting Apex in production).
  RLY_Release__c.Deletion_Count__c (exists) = deletions.size(); new LongTextArea field Deletions__c (32768) = comma-separated Type:Name; RLY_Release_Item__c rows for deletions with a new Checkbox Is_Deletion__c (backend owns objects; RLY_Release_Item__c may not exist in hub6/objects — create an RLY_Release_Item__c.object file with only the new field, or a CustomField entry in package.xml, whichever matches how RLY_Release__c fields are packaged).
  Dispatch mode 'hub' with input `deletions` = comma-separated Type:Name (RlyPipelineRun.inputs currently sends '' — fill it from the release).
  Promotion: carried releases' deletions are already in their merge commits (files removed), so nothing extra; Detail shows them.
  RlyReleasesController.Detail/Row: ADD List<String> deletions (Type:Name) on Detail (put it on the existing DetailLinks/RowKind parent classes to stay under PMD TooManyFields); Row: Integer deletionCount.
  Slack card: "Deletes: …" line (first 5, then "and n more").

## Pipeline (pipeline agent)
In raiseFromHub (mode hub): parse DELETIONS (Type:Name list, same parser as mode org). For each, remove the matching source files on the release branch under the source path (same mapping as above, reverse: ApexClass:X → classes/X.cls + classes/X.cls-meta.xml; LightningComponentBundle:x → lwc/x/ dir; CustomField:O.F → objects/O/fields/F.field-meta.xml; CustomObject:O → objects/O/ dir; Flow, Layout, PermissionSet, ApexPage, ApexComponent, StaticResource (+ the resource file), CustomTab, ValidationRule, RecordType, ListView, ApexTrigger, AuraDefinitionBundle). A deletion whose file isn't on the branch → raise.json status Failed with message "<Type> <Name> isn't in <branch>, so there's nothing to delete." git rm, commit together with the converted components (or alone if only deletions: the hub may send an empty zip or no zip — handle "no zip on the branch" when there are deletions and no components). The existing delta deploy plan already turns removed files into destructiveChangesPost.xml for validate and deploy — verify it does for both check-only and real deploys, and that quick deploy still works. PR body lists "Deleted from <org>". raise.json adds "deleted": [Type:Name]. Bump the version stamp to 10 in all pipeline files and re-copy hub6/staticresources/RLY_Pipeline_*.resource byte-identically. Commit on branch feature/pipeline-v10 from main, push (never to main), report.
Also: the hub sends no zip when a release has only deletions: the hub must still create the branch (from the developer branch as today) — agree: backend commits an EMPTY marker file `.relay-inbox/<REL>.deletions` containing the list when there is no zip; the pipeline accepts either the zip, the marker, or both.
